# CLAUDE.md — pyqt-omniviewer

Инструкция для разработчиков и их ассистентов (Claude Code / любой агент, читающий
`AGENTS.md` → это тот же файл). Про **что** строим — `SPEC.md` и `TASK.md`.
Здесь — **как вести работу**, чтобы несколько человек делали задачи параллельно
и каждый принимал свой PR сам.

---

## О проекте (коротко)

Двухпанельный десктоп-просмотрщик файлов на **PyQt6**. Хакатон: побеждает тот, чьё
приложение отобразит больше **типов файлов**. Отсюда приоритеты: ширина охвата важнее
полировки, каждый просмотрщик — минимальный («показать содержимое»), всегда есть
fallback (текст + hex + метаданные). **Всё in-process**: запуск внешних процессов
(`soffice`, `pdftoppm`, `ffmpeg`-CLI, `unrar`, …) и GUI-приложений запрещён.

Полное ТЗ и проектные решения — [`SPEC.md`](SPEC.md). Читай раздел SPEC по своей теме
перед тем, как брать задачу-просмотрщик.

### Метки

| Метка | Значение |
|---|---|
| `ready` | все блокеры закрыты — **можно брать** |
| `blocked` | ждёт закрытия issue-блокеров (см. раздел «Blocked by» в теле) |
| `in-progress` | **занято**, не брать (смотри assignee) |
| `foundation` / `tier-1` / `tier-2` / `delivery` / `post-mvp` | группа задачи |

Метки `blocked` / `ready` переключает автоматически workflow `.github/workflows/unblock.yml`
при закрытии/переоткрытии issue-блокера. Вручную их трогать не нужно.

## Цикл работы: одна issue → одна ветка → один PR

### 1. Выбрать задачу

```bash
gh issue list --repo asutenshi/pyqt-omniviewer --label ready --search "-label:in-progress"
```

Бери issue с `ready` и без `in-progress`. Проверь, что все её блокеры закрыты
(раздел «## Blocked by» в теле).

### 2. Занять — до начала работы

```bash
gh issue edit <N> --repo asutenshi/pyqt-omniviewer \
  --add-assignee @me --add-label in-progress --remove-label ready
```

Передвинь карточку в **In Progress** на доске. Теперь всем на всех ветках видно,
что задача занята: `gh issue list --label in-progress`.

### 3. Ветка от issue

```bash
gh issue develop <N> --repo asutenshi/pyqt-omniviewer --base main --checkout
```

Ветка создаётся от `main`, привязывается к issue на GitHub, имя — от заголовка.

### 4. Сделать — TDD по умолчанию

Работаем **test-first**, цикл red → green → refactor:

1. **Red.** Пишешь тест на внешнее поведение из «Критериев приёмки» — он падает.
   Для просмотрщика это тест через главный шов `ViewerRegistry` (см. раздел ниже):
   «по этому образцу реестр отдаёт такой-то класс, `viewer.load()` проходит без
   исключения, это не ошибочный виджет».
2. **Green.** Пишешь минимум кода, чтобы тест позеленел.
3. **Refactor.** Причёсываешь при зелёных тестах.
4. Повторяешь по каждому критерию приёмки.

Тест проверяет **поведение, а не реализацию** (SPEC → «Что считается хорошим тестом»):
«реестр по файлу выдаёт просмотрщик, и он грузит содержимое», а не «внутри вызвался
такой-то метод». Тесты не зависят от дисплея (`QT_QPA_PLATFORM=offscreen` / `xvfb`) и
гоняются на фиксированном наборе `demo/`.

Отступление от TDD допустимо только для чисто визуальной вёрстки виджета, где
поведенческого критерия нет; логика, разбор форматов, реестр, модели, утилиты —
всегда test-first.

Все чекбоксы из раздела «Критерии приёмки» issue должны быть закрыты и покрыты
тестом — это и есть Definition of Done.

Для задачи-**просмотрщика** результат — всегда один и тот же набор:

- модуль просмотрщика рядом с остальными просмотрщиками;
- **одна** запись в `ViewerRegistry` (append-only, см. ниже);
- образец в `demo/` (+ ветка в `demo/generate.py`, если формат скриптуется) — он же
  фикстура для теста;
- строки в таблицах смоук-теста: «файл → ожидаемый класс» и «путь → ожидаемый MIME»
  (написаны до реализации, шаг Red);
- тест на битый/обрезанный образец: просмотрщик отдаёт ошибочный виджет, не падает;
- строка в разделе README «Поддерживаемые форматы»;
- `## @brief` перед классом просмотрщика.

### 5. Проверить локально

```bash
ruff check .
QT_QPA_PLATFORM=offscreen pytest      # или: xvfb-run -a pytest
```

Весь набор зелёный (не только твои новые тесты), линт чистый. Красный тест — PR не мёржим.

### 6. PR и самопринятие

```bash
gh pr create --repo asutenshi/pyqt-omniviewer --base main --fill --body "Closes #<N>"
```

- В теле **обязательно** `Closes #<N>` — мёрж закроет issue и запустит автоматику.
- Дождись зелёного CI.
- Перед мёржем подтяни main: `git fetch origin && git rebase origin/main`, снова прогони тесты.
- Мёрж — свой PR принимаешь сам:
  ```bash
  gh pr merge --squash --delete-branch
  ```

### 7. После мёржа — происходит само

- issue закрывается по `Closes #<N>`;
- workflow `unblock` снимает `blocked` и ставит `ready` у задач, для которых это был
  последний открытый блокер (с комментарием в issue);
- карточка на доске уезжает в **Done**.

Если задачу пришлось бросить — верни всё назад: `--remove-assignee @me --remove-label in-progress --add-label ready`, карточка → Todo.

## Чтобы параллельные ветки не конфликтовали

- **Одна issue = свой набор новых файлов.** Просмотрщики не пересекаются: каждый —
  отдельный модуль. Двое над одним форматом не работают.
- **`ViewerRegistry` — общий шов, правки только append-only.** Добавляешь свою
  запись, чужие не трогаешь. Если меняется *структура* реестра или `BaseViewer` —
  это отдельная issue, обсуждение в её комментариях, остальные ждут.
- **Горячие точки слияния** (каждый тикет-просмотрщик их задевает → PR-ы конфликтуют
  между собой попарно):
  - `README.md` — таблицы «Работают сейчас» / «В планах»;
  - `demo/CREDITS.md` — таблица «Бинарные образцы»;
  - `demo/generate.py` — список в `build()` и base64-константы блобов;
  - `tests/test_registry.py` — таблицы `FILE_TO_VIEWER` и `PATH_TO_MIME` (+ ветки
    в `test_expected_mime`).

  **Правило разрешения — строго аддитивно:** берём структуру со стороны `main`
  (она новее), из обеих сторон **оставляем все строки**; свою фичу в `README`
  переносим из «В планах» в «Работают сейчас». Порядок строк не важен, дубли не плодим.
- **Не редактируй файлы, принадлежащие чужой `in-progress` задаче.**
  Список занятого: `gh issue list --repo asutenshi/pyqt-omniviewer --label in-progress`.
- **Каркас (#3–#10) трогает общее ядро** (главное окно, реестр, инфраструктура
  рендера, дерево, настройки). Эти задачи берём **по одной**, не параллелим между собой.
- **Никакого попутного рефактора общего кода.** Нашёл проблему — заведи issue.

### Rebase и force-push фиче-веток

**Rebase, не merge.** Перед созданием PR и перед мёржем:

```bash
git fetch origin
git rebase origin/main          # разрешаем горячие точки аддитивно (см. выше)
QT_QPA_PLATFORM=offscreen pytest # весь набор — сверяем с базой origin/main
git push --force-with-lease origin <branch>
```

`--force-with-lease` (не `--force`) — перезапись только если на remote нет чужих
коммитов поверх твоих.

**Если открытый PR завис, а `main` ушёл вперёд** — просто повтори rebase поверх
свежего `origin/main` и снова `--force-with-lease`. Это нормальный ход, а не авария.

**Ветки, которые уже были rebase + force-push поверх `main`:** `16-archive-viewer`,
`image-advanced-formats` (влит в #49), `17-markup-viewer`. Их удалённая история
переписана.

**Если у тебя есть локальная копия такой ветки** и на ней нет твоих собственных
коммитов:

```bash
git fetch origin
git checkout <branch>
git reset --hard origin/<branch>   # НЕ git pull — иначе получишь запутанный merge
```

Если твои коммиты на ней есть — `git rebase --onto origin/<branch> <старый-верх> <branch>`
или перенеси их черри-пиком.

**Base64-блобы в `demo/generate.py`** (`_HEIC_SAMPLE`, `_MP4`, `_DNG_SAMPLE`, …) —
однострочные литералы. Никогда не редактируй их вручную и не вставляй руками через
чат: любой сбой символа ломает `base64.b64decode`. Генерируй скриптом и вставляй
скриптом (regex-замена строки целиком), потом сверяй `python demo/generate.py` +
`pytest tests/test_demo_generate.py`.

## Соглашения

- **Язык** — код-комментарии, коммиты, PR, ответы ассистента: по-русски.
- **Коммит** — суть в заголовке (императив), тело — «зачем». Коммиты за Claude
  заканчиваются строкой:
  ```
  Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
  ```
- **Python 3.12**, `requires-python >= 3.10`. Линт — `ruff`.
- **TDD по умолчанию** (см. шаг 4): тест на поведение пишется до кода, красный →
  зелёный → рефакторинг. Ассистенту — использовать скилл `tdd`, если доступен.
  Главный шов для тестов — `ViewerRegistry` (вход: путь, выход: `BaseViewer`).
- **Doxygen** — `## @brief …` перед ключевыми классами/методами (`MainWindow`,
  `ViewerRegistry`, `BaseViewer`, каждый просмотрщик, сборщик метаданных,
  прокси-модель дерева). Обычные docstring тоже пишем. `doxygen Doxyfile` должен
  проходить без фатальных ошибок и без внешних фильтров.
- **Строго in-process** — ни один `subprocess`/`os.system`/внешний бинарник в коде
  продукта. Только библиотеки, линкуемые в процесс (в т.ч. нативные: libmupdf,
  libarchive, Qt Multimedia).
- **Безопасность** — имена файлов и записей архивов не подставляются ни в какие
  команды; пути из архивов проверяются на выход за пределы временной папки (Zip Slip);
  рекурсия по вложенным архивам ограничена по глубине и суммарному размеру.
